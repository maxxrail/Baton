# Northwind Goods mock commerce API

A fake store backend for **Northwind Goods**, a fictional DTC home-goods brand. Baton's tools call
it over HTTP the way they would call a real brand's commerce API. It ships in this repo so
everything runs offline.

- Separate FastAPI app, default port **8100**, SQLite (`MOCK_COMMERCE_DATABASE_URL`, default
  `sqlite:///./mock_commerce.db`).
- Interactive docs at `http://localhost:8100/docs` when running.
- Business rules are enforced **server-side**. A rule violation returns 4xx with a
  machine-readable code, never a silent success:
  ```json
  {"error": {"code": "RETURN_WINDOW_EXPIRED", "message": "the 30-day return window closed on 2026-05-21"}}
  ```
- All money is **integer cents** (`total_cents`, `amount_cents`).

## Running

```
uv run python -m scripts.dev                    # with the Baton API; reseeds on start
uv run python -m mock_commerce.seed             # reset + reseed the database only
uv run python -m mock_commerce.seed --generate  # rewrite data/seed/*.json from the generator
```

## Endpoints

| Method + path | Does | Rule / error codes |
|---|---|---|
| `GET /customers/lookup?email=` or `?phone=` | Find customers. Phone may match **several** accounts | exactly one param else 422 `INVALID_LOOKUP`; 404 `CUSTOMER_NOT_FOUND` |
| `POST /customers/{id}/verify` `{order_number, zip}` | Identity check → `{"verified": bool}` | true only if the order is this customer's **and** ships to that zip. Wrong zip, wrong order and someone else's order all return `false` |
| `GET /customers/{id}/orders` | Order summaries, newest first | 404 `CUSTOMER_NOT_FOUND` |
| `GET /orders/{order_number}` | Full order: items, refunds, returns, `refundable_cents`, `return_eligible_until` | 404 `ORDER_NOT_FOUND` |
| `POST /orders/{n}/cancel` | Cancel and refund the remaining balance (seeded cancelled orders look the same) | only `processing`, else 409 `ORDER_NOT_CANCELLABLE` |
| `POST /orders/{n}/address` `{line1, city, state, zip}` | Change shipping address | only `processing`, else 409 `ADDRESS_CHANGE_NOT_ALLOWED` |
| `POST /orders/{n}/return` `{reason}` | Create an RMA (201) | only `delivered` (409 `ORDER_NOT_RETURNABLE`); within 30 days of delivery (409 `RETURN_WINDOW_EXPIRED`); one open RMA per order (409 `RETURN_ALREADY_EXISTS`) |
| `POST /orders/{n}/refund` `{amount_cents, reason}` | Refund (201) | `amount_cents > 0` (422); never more than total minus prior refunds (409 `REFUND_EXCEEDS_BALANCE`) |
| `GET /subscriptions/{customer_id}` | List subscriptions | 404 `CUSTOMER_NOT_FOUND` |
| `POST /subscriptions/{id}/pause` · `/resume` · `/cancel` | Lifecycle | 409 `SUBSCRIPTION_NOT_ACTIVE` / `SUBSCRIPTION_NOT_PAUSED` / `SUBSCRIPTION_ALREADY_CANCELLED`; 404 `SUBSCRIPTION_NOT_FOUND` |
| `GET /customers/{id}/loyalty` | Points balance, lifetime points, tier (bronze < 1000 ≤ silver < 2500 ≤ gold) | 404 `CUSTOMER_NOT_FOUND` |

Mutating endpoints lock the order row (`SELECT ... FOR UPDATE` on Postgres), so concurrent refunds can't both pass the balance check.

What this API does **not** do: authenticate callers, rate-limit `verify` (zips can be brute-forced), or decide who may see what. Customer lookup
never returns the zip (it's the verification secret), but `GET /orders/{n}` does include the
shipping address. Keeping account data away from unverified customers is Baton's job, enforced
in the tool layer (Part 02), the same as with a real backend.

## Seed data

Generated by `src/mock_commerce/seed.py` from a fixed random seed and committed as JSON in
`data/seed/` (`customers.json`, `orders.json`, `subscriptions.json`, `loyalty.json`). A test
checks the committed files still match the generator.

- **50 customers** `cus_0001`–`cus_0050`, emails `@example.com`, phones in the fictional
  `555-01xx` range.
- **200 orders** `NW-10001`–`NW-10200` across `processing`, `shipped`, `delivered`, `returned`,
  `cancelled`, with ~400 line items from a 15-product catalog. Cancelled and returned orders
  are fully refunded.
- **20 subscriptions** `sub_0001`–`sub_0020` (coffee, tea, soap, candles), active or paused.
- **Loyalty accounts** for every customer.

Times are stored as day offsets (`"delivered_days_ago": 45`) and resolved when the data is
loaded, so the relative facts below hold whenever the store is (re)seeded.

### Tricky cases (fixed IDs; tests and simulations rely on them)

| Case | Data | Why it's there |
|---|---|---|
| Outside return window | `NW-10001` (cus_0001 Ava Thompson), delivered **45 days ago** | Return must fail with `RETURN_WINDOW_EXPIRED`; agent must not promise one |
| Inside return window | `NW-10002` (cus_0001), delivered 10 days ago, total $66.00 | Happy-path return/refund |
| Still processing | `NW-10003` (cus_0001), placed 1 day ago | Cancel and address change are allowed |
| Partial refund already issued | `NW-10004` (cus_0002 Liam Okafor), total $214.00, $40.00 refunded | Only $174.00 left; anything more is `REFUND_EXCEEDS_BALANCE` |
| Two accounts, one phone | `cus_0003` and `cus_0004` (both "Maya Nguyen") share `+15035550199` | Phone lookup returns two customers; the agent must disambiguate, not guess |

Verification for the fixtures: cus_0001 ships to zip `98101`, cus_0002 to `78701`,
cus_0003/cus_0004 to `97205`.
