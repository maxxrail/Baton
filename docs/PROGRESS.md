## Part 01 — what was built
- **AOP format + 8 AOPs** (`aops/*.md`, documented in `aops/README.md`): `return_item`, `where_is_my_order`, `cancel_order`, `change_address`, `refund_request`, `manage_subscription`, `loyalty_points`, `general_question`. All compile with zero diagnostics.
- **Models** (`baton.aop.models`): `AOP`, `Step`, `Transition(condition, target, implicit)`, `Terminal` (ESCALATE/RESOLVE), `Diagnostic`, `CompiledAOP`/`CompiledStep`, `AOPBundle`.
- **Parser** (`baton.aop.parser`): rule-based, deterministic. Frontmatter is a strict Pydantic model (`extra="forbid"`). Steps must be numbered 1..N. Jump phrasings, terminals, leading/inner conditions and `Otherwise` defaults; implicit fall-through. 45 phrasings table-tested (38 with a transition, 7 that must *not* parse as one), plus negated jumps and "in which case" rejected as parse errors with step + line.
- **Validator** (`baton.aop.validator`): all codes from the spec plus `PARSE_ERROR`. One fixture per code in `tests/aop/fixtures/bad/`, each asserting exactly that code.
- **Compiler** (`baton.aop.compiler`): `compile_aops(dir) -> AOPBundle`, raises `AOPCompileError` on any error; renders a step prompt per step from `prompts/aop_step.md` (step text, policies, allowed tools with flags, exits, verification note).
- **Router** (`baton.aop.router`): hashing-embedding pre-filter (top-k=5 + `general_question` fallback) then an LLM classifier through a `choose_procedure` tool whose `aop_id` is an enum of the candidates. Output is validated in code; anything not offered or malformed routes to `None`. `evals/router_cases.yaml` (40 cases) + `scripts/eval_router.py`.
  - **Router eval (2026-11-23, `claude-sonnet-5-5`, top_k=5): accuracy 40/40 = 100.0%.** Pre-filter recall@5 38/38 = 100.0%; pre-filter top-1 alone 27/38 = 71.1% (so the LLM stage is doing real work: it fixes the 11 cases where the best trigger match is wrong).
- **Tool registry** (`baton.tools.registry`, `baton.tools.schemas`): contracts for 13 Northwind tools; implementations come in Part 02.
- **Versioning**: `aop_versions` table (migration `0002`), `baton.aop.store.sync_versions` inserts only unseen (aop_id, source_hash, step_prompt_version) keys; `baton-aop compile` runs it.
- **Code review** (`code-reviewer` subagent) fixes applied: `else` only marks a default at a clause start ("something else, go to step 2" kept its condition); a trailing `if`/`unless` only guards the target just before it and an `if` before the target is read as "whether"; negated jumps and "in which case" are rejected; `continue/return/move ... to N` require the word "step"; `NO_TERMINAL`/`BAD_TARGET` steps no longer also produce a `CYCLE_WITHOUT_EXIT`; `aop_versions` keys on the step-prompt template version too (compiled JSON includes rendered prompts); customer text is `<`/`>`-escaped in the router's data tags; `none` is a reserved AOP id; the source hash ignores a leading BOM; `Router` accepts `prompts_dir`.
- **CLI** `baton-aop validate|graph|show|compile`; **API** `GET /aops`, `GET /aops/{id}`, `POST /aops/validate`.
- **Prompt loader** (`baton.prompts`): `load_prompt(name)` → text + version `name@sha256[:8]`.

## Part 02 — what was built
- **Tools** (`baton.tools.client`, `.errors`, `.northwind`): `CommerceClient` (httpx, 5 s timeout, GETs retried once on 5xx or transport errors, POSTs never retried, path segments URL-quoted). Store errors become `ToolError(code, customer_safe_message)`. The store's free text is never forwarded. `NorthwindTools.execute(name, args, ctx)` validates input, refuses account tools without a verified `ToolContext`, scopes orders and subscriptions to the verified customer (someone else's reads as `ORDER_NOT_FOUND`), and masks contact details in `lookup_customer` results.
- **State** (`baton.runtime.state`): `ConversationState` in `conversations.state` (JSON, migration `0003`). `customer_ref`/`status` are mirrored to their columns. Failed verifications are stored as hashes of (order, zip), never the zip.
- **Agent loop** (`baton.runtime.agent`): two short DB transactions per turn (load + store the customer message; save the reply, state and trace), none held during LLM or store calls. Routing when no AOP is active; `switch_procedure` re-routes mid-procedure (once per turn). Only the step's allowed tools are offered, plus `advance_step`/`switch_procedure`. Max 6 store tool calls and 10 model calls per turn. Unexpected errors produce an error trace and an apology (`raise_errors=True` in tests).
- **Guardrails** (`baton.runtime.guardrails`), all pure functions returning `GuardrailDecision`s, all written to the trace:
  - identity gate; one identity per conversation (`identity_switch`);
  - refund limit ($100 default via `BATON_REFUND_AUTO_LIMIT_CENTS`, counting earlier auto-refunds in the conversation) and live balance check (the runtime reads the order right before `create_refund`); either one exceeded means forced escalation;
  - per-step allow-list: the step's `@refs`, the identity tools, and read-only tools used anywhere in the AOP. Side-effect tools only on their own step;
  - reply checks: refund *action* claims need a refund tool success this turn; refund *status* statements also pass when an order looked up this turn has refunds; negated statements pass; order numbers must be the customer's own or typed by the customer; unprovided emails/phones are masked; length caps (web/cli 1200, sms 480, email 4000). A blocked reply gets one rewrite, then `FALLBACK_REPLY`;
  - escalation on 3 distinct failed verifications, 12 turns without progress, or an explicit request for a human (regex, tested both ways).
- **Escalation** (`baton.runtime.escalation`): `write_handoff` tool output validated into `HandoffSummary`, with a deterministic fallback from state and the tool log. Redacted, stored on the state and as a `system` message.
- **Traces** (`baton.runtime.traces`): `TurnTrace` as listed in CLAUDE.md, plus route decision, step before/after, rejected drafts and reply source. `zip`/`line1` are masked and everything else goes through `redact_value`.
- **API** (`baton.api.conversations`): `POST /conversations`, `POST /conversations/{id}/messages`, `GET /conversations/{id}`, `GET /conversations/{id}/traces`. The agent and engine are built on first use; with `BATON_LLM=fake` the API returns 503 with a fix-it message.
- **CLI** `baton-chat [--trace]` (`baton.channels.cli`): in-process agent against `MOCK_COMMERCE_URL` and `DATABASE_URL`. Preflight checks the migrations and the store. Exits 2 with a clear message under `BATON_LLM=fake`.
- **Live check** (2026-11-23, `claude-sonnet-5-5`): `docs/samples/chat-return.md`. It found two false positives in the refund-claim check ("No refund has been issued yet", "nothing has been refunded"). Both are fixed and pinned by tests.
- **Code review** (`code-reviewer` subagent) fixes applied:
  - Two concurrent turns could both pass the refund limit: added a per-conversation **turn lease**, a conditional UPDATE on `conversations.turn_lease_until` that is atomic on SQLite and Postgres and expires after 5 minutes. A second message during a turn gets `ConversationBusyError` (API 409).
  - The refund check failed open when the order read failed: it now checks the amount and the conversation total first, then **blocks** (`refund_unverifiable`) if the order can't be read. Refunds already on the order count toward the limit, so the same order can't be split across conversations.
  - Verification ZIPs reached the logs: `redact()` can't recognise ZIPs or street addresses, so `agent_turn` now logs the message length, not its text. A test asserts the ZIP never appears.
  - Refund-claim gaps ("I've processed your refund", "Your refund is processed", "You'll be refunded $250", "Refund issued!") are closed. A backed claim must also state an amount that matches a real refund (a $50 refund no longer backs "I've refunded $500"). Conditional wording ("once we receive the item") passes.
  - Order numbers are canonicalised before the foreign-order check (`NW 10004`, `nw10004`, `#10004`).
  - POSTs are no longer retried on a 5xx (the store doesn't dedupe, so a retry could pay twice), and the unused `Idempotency-Key` header was removed.
  - Lower-severity fixes: tool inputs strip whitespace; only forward `advance_step` moves count as progress; the logged step target is redacted and capped; the guardrail's own balance read is traced (`source: "guardrail"`); card numbers in replies are masked.


## Part 03 — what was built
- **Help center** (`data/kb/`, 28 articles, documented in `data/kb/README.md`). Realistic and overlapping on purpose (returns / exchanges / refunds / damaged items / warranty all touch the return window). Two deliberate conflicts: `return-policy` (30 days, 2026-02-01) vs `return-policy-2024` (60 days, free labels), and `shipping-costs` (free over $75, 2026-06-15) vs `free-shipping-offer-2025` (free over $50). Facts match the AOP policies and the mock store (30-day window, cancel only while processing, tiers at 1000/2500).
- **Articles + chunking** (`baton.knowledge.articles`, `.chunking`): strict frontmatter (`extra="forbid"`, id must equal the file name). Sections split at headings with their heading path, packed into chunks that close at 300 tokens or before passing 500, oversized sections split at paragraph breaks with the heading repeated, a <100-token tail folded into the previous chunk. Heading-only sections (an H1 directly above an H2) are dropped, since their text lives in the children's paths. The real KB gives 30 chunks (`return-policy` and `shipping-times-us` have two each).
- **Ingest** (`baton.knowledge.ingest`, `baton-kb ingest`, table `kb_chunks`, migration `0004`): incremental by `content_hash = sha256(embedder name + title + heading path + text)`. Unchanged chunks keep their row and vector (only bookkeeping fields like `updated_at` are refreshed), new hashes are embedded in one batch, leftovers and deleted articles are removed. Tests: a second run embeds nothing and leaves ids/vectors identical; editing one article re-embeds exactly its changed chunk (also within a two-chunk article); a date-only edit re-embeds nothing; switching embedders re-embeds everything, and the old index is refused at load.
- **Retrieval** (`baton.knowledge.retrieve`): own BM25 (title and heading path counted twice) + embedding cosine, reciprocal-rank fusion (k=60, BM25 weight 2.0), top-5 from 10 candidates. **Newer wins:** among candidates, an older article in the same category whose closest chunk is >= 0.40 cosine to a newer article's is moved directly below it. **Coverage:** IDF-weighted share of the query's terms found in the best of the top 3 chunks (unknown terms at full weight); below 0.33 the result is `covered=False`. Optional `LLMReranker` (`BATON_KB_RERANK=true`, `prompts/rerank.md`), validated in code: it can only reorder; bad output or an exception keeps the fused order, and the recency rule runs after it.
- **Retrieval eval** (`evals/retrieval_qa.yaml`, `scripts/eval_retrieval.py`, gate in `evals/thresholds.yaml`, also a pytest and a CI step). 40 questions written in customer phrasing before tuning, 8 not answerable. **HashingEmbedder (2026-11-24): recall@5 0.969 (31/32), MRR 0.768, abstention accuracy 0.900** (abstained on 7/8 unanswerable, answered 29/32 answerable). The one miss is "do you deliver to Australia?" (needs knowing Australia isn't Canada/US). Abstention errors: "customs/import fees to Toronto", "rust off my skillet", "gold status" (vocabulary the KB doesn't use) and "name engraved on the knife" (both words appear in the KB). No Voyage key was available, so there are no real-embedder numbers yet: run `uv run python -m scripts.eval_retrieval --embedder voyage`.
- **`search_knowledge` tool** (registry + `NorthwindTools`): `requires_verification=False`, offered on every step of every procedure by `allowed_tools`. Returns passages with `article_id`, section, `updated_at`, text and `cite_as`, plus `covered` and a note telling the model to abstain when not covered. Without a KB it reports `KNOWLEDGE_UNAVAILABLE`. `general_question` v2 references it at step 2.
- **Grounding guardrail** (`baton.knowledge.grounding`, `prompts/grounding.md`): runs in `Agent._finish` after the deterministic reply checks whenever the turn searched the KB, the reply cites `[kb:...]`, or a procedure that references `@search_knowledge` was active (so an answer written *without* searching is still checked, against no KB evidence). The reply is split into sentences **in code**; the judge (structured `report_grounding` tool) labels each sentence `claim`/`other`, `supported`, `sources`. Code then passes it (adding a citation to supported KB claims that lack one), removes unsupported claims and appends an offer of a teammate ("trimmed"), or replaces the whole reply with `ABSTAIN_REPLY` ("abstained"). A "supported" label must name a source that is actually in the evidence. **Fails closed:** an exception, no tool call, malformed output or unlabelled sentences count as unsupported. Evidence = this turn's passages + the previous search's (via `state.kb_evidence`) + this turn's account tool results + the state summary + the active procedure's policies. Edited text goes back through `check_reply` (length/PII).
- **Citations:** grounding strips tags for articles that weren't retrieved, so every `[kb:id]` in a sent reply resolves to a real, retrieved article. `AgentReply.citations` (id, title, URL from `BATON_KB_BASE_URL`) is in the API response. `baton.channels.citations` renders them per channel (markdown links / footnotes / one SMS link) and collapses repeated tags. `baton-chat` prints footnotes.
- **Traces:** `knowledge_searches`, `grounding` (full outcome), `citations`, `reply_source="abstention"`, a `grounding` guardrail decision, a `grounding` LLM purpose and prompt version, and the original draft in `rejected_replies` when grounding edits it.
- **Optional real embedder:** `VoyageEmbedder` (plain httpx, batched, normalised, errors never echo the body), `BATON_EMBEDDER=voyage` + `VOYAGE_API_KEY`.
- **Runtime fix found live:** the model often writes its answer in the same response as `advance_step(RESOLVE)` and ends with "Anything else?". The loop used to send only the final text, so the answer was dropped (seen on the Canada question). Text written alongside tool calls is now kept and joined with the final text, and the joined text goes through every reply check (`test_a_false_claim_written_next_to_a_tool_call_is_still_checked`).
- **Code review** (`code-reviewer` subagent) fixes applied:
  - The live-run fix kept text written *before* tool results, so "I've cancelled it" next to a cancel that failed would have been sent. Now a draft is kept only if every tool call in that response succeeded (`test_a_draft_next_to_a_failed_tool_call_is_discarded`, `test_a_claim_written_next_to_a_blocked_tool_call_is_discarded`). The model is told its draft will be sent (`DRAFT_KEPT_NOTE`), and a final reply that repeats a draft isn't sent twice.
  - An abstention could hide runtime-verified facts: after a successful refund (with a failing judge) the customer would hear "I'm not sure", and during an escalation they'd be asked "would you like a teammate?". Abstention now keeps `ESCALATION_REPLY`, or a runtime-written list of the side effects the store confirmed ("I've issued a refund of $25 on order NW-10004") plus the hedge note.
  - A Voyage outage (`EmbeddingError`) crashed the turn; the search now reports `KNOWLEDGE_UNAVAILABLE`.
  - `kb_chunks` ids could be reused by SQLite after a re-ingest, so a stale `state.kb_evidence` id could point at different text. The table now uses `sqlite_autoincrement` (Postgres sequences never reuse ids).
  - On SMS, re-truncation after grounding could cut off the offer of a teammate, and `truncate` could cut a citation tag in half. The body is now truncated, never the hedge note, and truncation never ends inside a `[...]`.
  - Sloppy tags (`[KB: Return-Policy]`, `[kb: x ]`) slipped past the strict citation regex and would show raw; they are normalised before any check. `AgentReply.citations` is built only from retrieved articles, not just any article in the KB.
- **Live check** (2026-11-24, `claude-sonnet-5-5`, `docs/samples/chat-knowledge.md`): the Canada answer was searched, cited and grounded (3/3 claims supported). "Do you price match?" got "I'm not sure ... would you like a teammate?" (0 claims, nothing removed).

## Part 04 — what was built
- **Channel adapters** (`baton.channels.base`): `InboundMessage` (`conversation_key`, `customer_hint`, `text`) and a `ChannelAdapter.format_reply` per channel. Web: markdown with numbered citation links and a Sources list. Email: citations as footnotes, markdown stripped, signature (the operator's name on human replies). SMS: GSM-7/UCS-2 segment counting, smart punctuation mapped to GSM so a reply doesn't fall into 70-char UCS-2 segments, cut at a word to at most 2 segments with `... Full answer: <web>/widget?c=<id>&t=<signed token>` (`baton.channels.links`, 7-day expiry; no secret = no link); a cited answer links its article. Stored replies keep channel-neutral `[kb:id]` tags; citations are saved on the message (`messages.meta`) so a transcript re-renders later.
- **One conversation path** (`baton.channels.service.ConversationService`): web, email and SMS all call `customer_message` → `Agent.handle_turn` → `deliver` through the conversation's own channel. Webhooks wait out a busy conversation for longer than a turn lease can last (`wait_if_busy`), so a second text during a reply is queued, not dropped (closes the Part 02 gap); if the turn still fails, the email Message-ID / Twilio MessageSid is forgotten so the provider's retry is processed. Provider failures are logged and reported, never lose the stored reply.
- **Web chat** (`baton.api.chat`): `WS /ws/chat/{id}` (typing activity, agent/teammate messages, status, errors) plus the HTTP fallback `POST /conversations/{id}/messages` (now returns the rendered `body` too). `request_human` frames take the same escalation path as typing "talk to a person".
- **Streaming**: `LLMClient.stream()` (Anthropic via the SDK's stream helper, `FakeLLM` replays chunks). The agent streams when a listener is attached and announces tool calls as soon as the model starts writing them (`TurnEvent` activity: `routing`, `thinking`, `tool:<name>`, `checking`, `handoff`). See Decisions for why reply text is not streamed.
- **Email** (`baton.channels.email`, `POST /channels/email/inbound`): generic JSON shape, `X-Baton-Webhook-Secret`. Threading by `In-Reply-To`/`References` (every inbound and outbound Message-ID is stored in `channel_threads`), then same sender + normalised subject within 7 days, else a new conversation. A thread id only counts when the sender is the conversation's customer. Subject threading is used only when the provider says the sender authenticated (`authenticated`: SPF/DKIM passed), since `From` is forgeable. A repeated Message-ID (webhook retry) is ignored. Quoted history ("On ... wrote:", Outlook headers, `>` lines, signatures) is stripped before the agent sees it. Senders: `ConsoleEmailSender` (prints a redacted copy), `ResendEmailSender` (httpx), `SmtpEmailSender` (STARTTLS).
- **SMS** (`baton.channels.sms`, `POST /channels/sms/inbound`): Twilio signature (HMAC-SHA1 over URL + sorted params, constant-time compare, `BATON_PUBLIC_URL` for proxies), checked before anything else. Body parsed with the stdlib (no `python-multipart`). STOP/START/HELP only when they are the whole message; keywords never reach the agent; opted-out numbers get nothing sent. Threaded by phone (24 h window; an escalated conversation is always continued). A repeated `MessageSid` (Twilio retry) is ignored. Senders: `ConsoleSmsSender`, `TwilioSmsSender` (httpx).
- **Human handoff** (`baton.runtime.handoff`, `/ops/conversations/{id}/takeover|reply|handback`): while `escalated` the agent stores and traces customer messages (`reply_source="human_owned"`, `AgentReply.replied=False`) but makes no model call and sends nothing. An operator can take over any conversation, reply as `human_agent` through the original channel (email in the same thread, SMS, or pushed to the widget), then `resolve` or `return_to_agent`. Hand-back ends the procedure and restarts the no-progress counter, but keeps identity and failed verification attempts. Every operator action takes the turn lease (409 while the agent is mid-reply) and leaves a `system` note.
- **Console API + auth** (`baton.api.console`, `baton.api.auth`): shared-secret login (`BATON_CONSOLE_SECRET`) → HttpOnly SameSite=Strict cookie `name|issued|HMAC` (12 h), or `Authorization: Bearer <secret>`. No secret = 503, never open. Cookie-authenticated writes and `/ws/ops` must come from the web app's (or API's) Origin. The cookie is `Secure` whenever the web/public URL is https (TLS-terminating proxies). `GET /ops/conversations` (status/channel filters, last message, counts in two queries), `WS /ws/ops` pushes inbox events from an in-process `EventHub`. `GET /conversations/{id}` and `/traces` are now operator-only; customers get `GET /conversations/{id}/messages` (no system notes, no state; non-web transcripts need the signed token). `POST /conversations/{id}/messages` only accepts web conversations.
- **Web app** (`web/`, React 18 + Vite 5 + TS + Tailwind 3): `/widget` (launcher + panel, transcript resume via localStorage, reconnecting socket, activity-aware typing indicator, citations as links, "Talk to a human", HTTP fallback), `/widget?c=<id>&t=<token>` read-only transcript (the SMS link target), `public/widget.js` iframe embed snippet (origin-checked postMessage resize), `demo-store.html`; `/console` (login, live inbox with filters and per-row AI activity, conversation view with handoff summary, take over / reply / return to AI / resolve, trace panel, AOP browser with Mermaid and a validate-a-draft box). Markdown is rendered to React elements, never HTML; only http(s) links; customer text is never parsed.
- **Dev**: `scripts/dev.py` also starts Vite (finds `npm` on Windows even off PATH, skips with a hint if `node_modules` is missing) and injects dev-only defaults for unset channel secrets into its child processes. `scripts/simulate_inbound.py` posts signed SMS / secret-bearing email webhooks and waits for the reply.

Acceptance tests: `tests/channels/test_same_logic.py`, `tests/channels/test_sms.py`, `tests/channels/test_email.py`, `tests/channels/test_handoff.py`, `tests/channels/test_trace_fixture.py` + `web/src/console/TracePanel.test.tsx`, `web/src/widget/MessageBubble.test.tsx`.

    - **The handoff note said a verified customer was "unverified"** and that nothing had been checked, telling the teammate to distrust a correct answer. The note writer only saw the escalation turn's (empty) tool log. It now gets the runtime's verified state (marked authoritative in `prompts/handoff.md`) and the whole conversation's tool log from stored traces (`tests/runtime/test_handoff_context.py`).
    - **An answer was lost:** "How many loyalty points do I have?" got "Is there anything else you'd like to know about your points?". Sonnet 5.5 returns text written between tool calls as a hidden progress block, so the answer written next to `advance_step(RESOLVE)` never arrived, and the model then only wrapped up. When a tool-call response has no visible text and nothing has been kept for the customer yet, the runtime now says so (`NOTHING_SENT_NOTE`). After the fix the same question got the full balance, lifetime points and tier.
- **Code review** (`code-reviewer` subagent) fixes applied:
  - **Stale turn after a takeover.** A turn that ran past its 5-minute lease could save over an operator's takeover (status back to `open`) and send an agent reply into a human-owned conversation. `acquire_turn` now returns the lease as a token; `_save` checks it is still held (`holds_turn`) and raises `LeaseLostError` instead of saving or replying, and `release_turn` only frees its own lease (`test_a_turn_that_outlived_its_lease_cannot_overwrite_a_takeover`).
  - **Dropped webhook messages.** The background retry gave up after 20 s while a lease lasts 5 minutes, and the email Message-ID was recorded before the turn, so the provider's retry was ignored as a duplicate. Now the wait outlasts a lease and the id is forgotten on failure (`test_a_text_that_waited_out_a_stuck_turn_is_retried_not_lost`, `test_an_email_that_waited_out_a_stuck_turn_is_retried_not_lost`). Twilio `MessageSid`s are deduplicated (`test_a_twilio_retry_runs_one_turn`); a retried email no longer creates an orphan conversation.
  - **Forged `From` into a verified conversation.** Subject threading required only a matching `From`. It now also requires the provider's authentication verdict (`test_a_forged_from_cannot_thread_into_a_verified_conversation_by_subject`).
  - **SMS link was a permanent bearer token** that also let anyone `POST` into the SMS conversation and read the reply over HTTP. HTTP messages now only reach web conversations, and non-web transcripts need a signed, expiring token (`test_http_messages_only_reach_web_conversations`, `test_sms_transcripts_need_a_signed_unexpired_link`).
  - **Origin checks** on cookie-authenticated console writes and `/ws/ops` (SameSite doesn't separate same-site origins) (`test_cookie_writes_from_another_origin_are_refused`, `test_inbox_socket_refuses_other_origins_and_forged_cookies`).
  - Smaller: sync DB work moved off the event loop in the SMS webhook and chat socket; the chat socket survives non-JSON frames and turn failures; a non-ASCII cookie is rejected instead of raising `TypeError`; `Secure` cookies behind TLS proxies; a bad channel config is a 503 (typed `get_service` replaces an untyped lazy proxy); `simulate_inbound` redacts what it prints; transcript-token timestamps are hex so log redaction doesn't mistake them for phone numbers.
- **Live re-check after the fixes**: a long SMS answer arrived as 2 segments ending in a signed link; the link opened the transcript (200) and the bare id was refused (404). HELP was answered in TwiML without the agent.

## Decisions
- 2026-11-23 — Default model `claude-sonnet-5-5` — the part asks for "a current Claude Sonnet model"; override with `BATON_MODEL`.
- 2026-11-23 — `AnthropicClient` ignores `temperature` — the current Claude API rejects sampling parameters (SDK 2.x doesn't accept them). The `LLMClient.complete` signature keeps `temperature` as the part specifies, documented as a hint.
- 2026-11-23 — `AnthropicClient` calls `client.beta.messages.create` with the server-side fallback beta (`fallbacks="default"`), so a safety-classifier refusal is retried on a fallback model by the API. Disable with `BATON_LLM_FALLBACKS=false`. `stop_reason="refusal"` is surfaced to callers either way.
- 2026-11-23 — `LLMResponse.content` keeps every block in order, including thinking blocks, so the runtime can append the assistant turn to history unchanged (the API requires thinking blocks be replayed as-is).
- 2026-11-23 — AnthropicClient test uses `httpx2.MockTransport` instead of respx. The anthropic SDK 2.x is built on `httpx2`; respx only patches `httpx`. This still exercises real request serialisation and response parsing with no network. respx stays a dev dependency for testing our own httpx clients (e.g. the mock-commerce tool client in Part 02).
- 2026-11-23 — Seed JSON stores times as day offsets (`delivered_days_ago: 45`) resolved at load time, so "delivered 45 days ago" stays true no matter when the store is seeded. `scripts/dev.py` reseeds on every start (`--keep-data` to skip).
- 2026-11-23 — Mock commerce money is integer cents everywhere; business-rule violations are 409 with `{"error": {"code", "message"}}`, input validation is 422.
- 2026-11-23 — Phone lookup returns a list (two seeded accounts share a phone); `verify` returns `false` for wrong zip, unknown order and someone else's order alike, so it leaks nothing.
- 2026-11-23 — Mock commerce has its own tiny settings (`MOCK_COMMERCE_DATABASE_URL`) and SQLAlchemy `Base`; it doesn't import `baton`, because it stands in for an external system. It uses `create_all` rather than Alembic (it's a disposable mock).
- 2026-11-23 — Pre-commit ruff hooks switched from the pinned `ruff-pre-commit` v0.8.4 repo to `repo: local` running `uv run ruff`, so pre-commit, CI, and the Claude Code hook all use the version in `uv.lock`. Migrations are linted/formatted like everything else.
- 2026-11-23 — `messages.id` is an integer autoincrement (it defines message order); conversations and traces keep uuid-hex string ids.
- 2026-11-23 — `baton.db.UTCDateTime` rejects naive datetimes on write and always returns aware UTC on read.
- 2026-11-23 — A minimal `baton/runtime/redact.py` (emails, phones, card numbers) was added in Part 00 because this part introduces logging and CLAUDE.md forbids PII in logs. Part 02 can extend it for traces.

- 2026-11-23 — (Part 01) **Conditions are sentence-scoped.** `If X, do Y and RESOLVE.` is conditional; `If X, do Y. RESOLVE.` resolves always. This keeps the parser predictable; the validator's `UNREACHABLE_STEP` message explains the pattern when it bites (it did on the first draft of two Northwind AOPs).
- 2026-11-23 — (Part 01) `ESCALATE`/`RESOLVE` are recognised only in upper case, so prose ("we'll resolve it") never ends a procedure.
- 2026-11-23 — (Part 01) `NO_TERMINAL` is reported per step: a reachable step with no default exit (only possible for the last step, since others fall through). `CYCLE_WITHOUT_EXIT` is reported for a trapped strongly connected set of steps. Steps with a `BAD_TARGET` are excluded from those checks, so each mistake is reported once at its root.
- 2026-11-23 — (Part 01) Added `PARSE_ERROR` (not in the spec's list) so malformed files surface as diagnostics with line numbers instead of exceptions.
- 2026-11-23 — (Part 01) `aop_versions.version` is the author's frontmatter version; uniqueness is on (aop_id, source_hash, step_prompt_version), because the stored compiled JSON contains the rendered step prompts and must match what the agent saw. Editing an AOP without bumping `version` still stores a row and `sync_versions` warns (a template-only change doesn't warn). Source hash normalises CRLF→LF and strips a BOM so editors and OSes don't create versions. Compiling is assumed single-writer (documented in `store.py`). Migration `0002` was amended in place before merge since it hasn't shipped.
- 2026-11-23 — (Part 01) Every Northwind tool except `lookup_customer`/`verify_customer` is `requires_verification=True` (reads of account data included), so all account AOPs set `requires_verification: true`. The validator enforces this only for side-effecting tools, as specified; the Part 02 identity gate covers the rest.
- 2026-11-23 — (Part 01) Router pre-filter drops tokens that appear in the triggers of more than half the AOPs (`customer`, `wants`, `the`, ...) and scores the previous customer turn separately (×0.9) instead of concatenating it. Both came from measuring recall on the fixture: without them 2/38 labeled cases fell outside the top 5. One trigger was also added to `return_item` (size/colour exchanges). With these, recall@5 = 38/38 and top-1 by similarity alone = 27/38.
- 2026-11-23 — (Part 01) `LLMClient` has no `tool_choice`, so the router can't force the tool call; it also accepts a bare JSON answer and otherwise routes to `None`.
- 2026-11-23 — (Part 01) The API compiles AOPs in `create_app`, so a broken AOP directory fails startup (and tests) rather than live conversations.
- 2026-11-23 — (Part 02) **The model signals progress, the runtime decides.** `advance_step` must match a compiled transition from the current step; anything else is a tool error plus a `step_transition` block in the trace. There is no automatic step inference: deterministic and testable beats clever.
- 2026-11-23 — (Part 02) **Topic changes go through `switch_procedure`** rather than routing every turn. That saves one LLM call per turn, and the model with the full context is best placed to notice a new topic. The router still validates the new choice, and only one switch per turn is allowed.
- 2026-11-23 — (Part 02) **"Read-only lookups" in the allow-list** = identity tools + read-only tools referenced anywhere in the active AOP. Without this, the model has to fake a step jump just to read an order the customer named at step 1. Side-effect tools stay pinned to their step.
- 2026-11-23 — (Part 02) **Ownership is enforced in the tool layer** (it needs store data), and the runtime's identity gate is enforced again there (`NOT_VERIFIED`), so calling the tools directly is still safe.
- 2026-11-23 — (Part 02) **Refunds over the balance escalate**, as the spec says ("above that → forced escalation"), rather than being blocked back to the model. The balance comes from a fresh `get_order` right before the refund, not from cached state.
- 2026-11-23 — (Part 02) A failed verification attempt = a distinct (order, zip) pair. Trying the same pair against two accounts that share a phone counts once, so a real customer with a shared household phone isn't penalised; brute-forcing zips is still capped at 3.
- 2026-11-23 — (Part 02) Cross-turn history sent to the model is text only. Earlier tool calls aren't replayed; the state summary (verified identity, lookup candidates, known orders, slots) carries what matters. This keeps prompts bounded and avoids replaying stale tool results.
- 2026-11-23 — (Part 02) Guardrail-forced escalations use a fixed runtime reply (`ESCALATION_REPLY`). A procedure's own `ESCALATE` lets the model write the reply (still output-checked), then hands off.
- 2026-11-23 — (Part 02) Starlette's `TestClient` (an `httpx.Client` with an in-process ASGI transport) serves as the "ASGI transport" for the mock store in tests. The runtime is synchronous, like `LLMClient`, so it uses a sync client; no sockets are opened.
- 2026-11-23 — (Part 02) **Deviation from the spec:** "one retry on 5xx" applies to GETs only. POSTs (cancel, refund, return, ...) are never retried, because the mock store, like many real ones, doesn't dedupe and a 5xx can arrive after the write committed. The agent reports `SERVICE_UNAVAILABLE` and can re-check state with a GET.
- 2026-11-23 — (Part 02) `cancel_order` refunds the full charge without the $100 check. That's the cancel policy, not a discretionary refund, and the tool is only allowed on the procedure's confirmation step. It's not counted in `auto_refunded_cents`.
- 2026-11-23 — (Part 02) Turns are serialised per conversation by a DB lease rather than an in-process lock, so it holds across API workers. Migration `0003` was amended in place before merge (not shipped yet).
- 2026-11-23 — (Part 02) `baton-chat` runs the agent in-process (it only needs the mock store), so it doesn't depend on the API port, which is taken on the dev machine.
- 2026-11-24 — (Part 03) **Retrieval tuning, measured on `evals/retrieval_qa.yaml`:** with the hashing embedder, BM25 alone scores recall@5 0.969 and the vectors alone 0.750, so equal fusion weights (0.938) let the weaker signal pull results down. BM25 weight 2.0 restores 0.969 and lifts MRR (0.704 to 0.768, together with the heading-only-section fix), and is stable across rrf_k in {10, 30, 60} and b in {0.5, 0.75, 0.9}. The weight is a `RetrievalConfig` field; with a semantic embedder, equal weights may be right, so re-measure then.
- 2026-11-24 — (Part 03) **Newer wins by demotion, not promotion.** The first version moved a newer same-topic article *up*; that pulled a barely relevant `return-policy` chunk into the top 5 for "my mug arrived cracked" and pushed out the right answer (recall dropped to 0.938). Demoting the older article below the newer one keeps relevance order and lets outdated text fall out of the top k. "Same topic" = same category and the articles' closest chunks have cosine >= 0.40; the conflict pairs measure 0.41-0.44 and the closest non-conflicting same-category pair 0.37 (`test_the_old_article_wins_on_fusion_alone_so_the_rule_is_doing_the_work`).
- 2026-11-24 — (Part 03) **Coverage threshold 0.33** was picked on the same 40 questions (0.30 and 0.33 both give 0.90; 0.33 abstains on one more unanswerable question). There's no held-out set, so treat 0.90 as an optimistic estimate. A bigram-coverage variant was tried and rejected: 13 of 32 answerable questions have zero bigram overlap.
- 2026-11-24 — (Part 03) **The judge labels, code edits.** The judge never rewrites the reply: it labels numbered sentences that code produced, and code decides what to remove. That makes the guardrail deterministic given the labels, testable with a scripted judge, and immune to a judge that "fixes" the answer into a new hallucination.
- 2026-11-24 — (Part 03) **Grounding fails closed.** A broken or partial judge answer means abstention, not an unchecked answer. That costs a correct answer now and then; for policy claims, an invented answer is worse.
- 2026-11-24 — (Part 03) **Evidence includes account data, state and procedure policies**, not only KB passages. Otherwise a reply in `return_item` that searched the KB *and* states the order's delivery date would lose the (true) account sentence. Only KB sources produce citations.
- 2026-11-24 — (Part 03) **Grounding runs after `check_reply`, on the accepted text**, so a draft that's going to be rewritten for a refund claim doesn't cost a judge call. The edited text goes back through `check_reply` for length and PII.
- 2026-11-24 — (Part 03) Article-level citations (`[kb:article_id]`), not chunk-level: the reader clicks an article, and ids stay stable when chunking changes.
- 2026-11-24 — (Part 03) Own ~40-line BM25 rather than `rank-bm25`: no dependency, and its idf is needed for the coverage signal anyway.
- 2026-11-24 — (Part 03) Voyage via plain httpx rather than its SDK: one endpoint, no new dependency, and mockable with `httpx.MockTransport`.
- 2026-11-24 — (Part 03) The `Embedder` protocol gained `name`; it's part of every chunk's hash and stored per row, so a mixed-embedder index can't happen silently.
- 2026-11-24 — The mock store's default port moved from 8100 to 8300 (`scripts/dev.py`, `MOCK_COMMERCE_URL` default, `.env.example`, docs): 8100 is taken on the dev machine. Part files and earlier CHANGELOG entries still say 8100 as a historical record.

- 2026-11-24 — (Part 04) **Reply text is not streamed to the customer (deviation from the spec).** The spec asks to stream agent text when the LLM supports it. Every reply passes `check_reply` and (for help-center answers) the grounding judge, which may rewrite or abstain, and a streamed sentence can't be unsent. So `LLMClient.stream()` exists and the agent uses it, but only to announce progress (which tool the model is starting to call) as a typing indicator; the text goes out once, after the guardrails.
- 2026-11-24 — (Part 04) **Escalated means silent.** Part 02 sent a fixed holding reply to every message after an escalation; the spec says the agent stops replying. Messages are still stored and traced (`reply_source="human_owned"`), so the teammate and Watchtower see them.
- 2026-11-24 — (Part 04) **One service, not per-channel logic.** Channels differ only in inbound parsing and outbound formatting; everything else goes through `ConversationService.customer_message`, which is what the "same tool calls on every channel" test pins.
- 2026-11-24 — (Part 04) **Webhooks answer first, work in the background.** Twilio times out after 15 s and an agent turn with tools can take longer. The inbound webhook validates, threads and returns; the turn and the outbound send happen in a background task. Busy conversations are waited out rather than refused.
- 2026-11-24 — (Part 04) **Email threading trusts our Message-IDs, and subjects only with sender authentication.** Our outbound Message-IDs are random, so quoting one proves the sender received our email (and it must also be the conversation's customer). Subject + `From` is forgeable, so it only threads when the provider passes an SPF/DKIM verdict (`authenticated`). Providers that don't send one simply start a new conversation per unthreaded email.
- 2026-11-24 — (Part 04) **GET /conversations/{id} and /traces became operator-only** (deviation: they were open in Part 02/03). The console needs them and adds auth anyway; leaving full state and traces public next to a logged-in console made no sense. The widget uses the new customer-safe transcript endpoint.
- 2026-11-24 — (Part 04) **Shared-secret console auth via a signed cookie**, not the raw secret in the cookie: changing the secret logs everyone out, the cookie can't be forged, and it works for the console's WebSocket (browsers can't set headers on WebSockets). Bearer auth stays for scripts.
- 2026-11-24 — (Part 04) **Twilio's form body is parsed with `urllib.parse.parse_qsl`**, not `python-multipart`: no new dependency, and the signature is checked over exactly the parsed parameters.
- 2026-11-24 — (Part 04) **Live updates are an in-process event hub plus "refetch on event".** The console re-reads the inbox (and the open conversation) when an event names it; events carry ids, not data. Simple, robust to dropped events, and enough for one API process (see Known gaps).
- 2026-11-24 — (Part 04) **The widget is an iframe** (`widget.js` mounts `/widget?embed=1`): the host page's CSS can't break it, it can't read the host page, and the only message it posts out is open/closed.
- 2026-11-24 — (Part 04) **Markdown is rendered by a ~100-line renderer into React elements**, not a markdown library + `dangerouslySetInnerHTML`: replies can't inject markup, only http(s) links become anchors, and the subset (bold, italic, code, links, lists, citations) is what the agent writes.
- 2026-11-24 — (Part 04) **SMS replies are mapped to GSM-7 first** (smart quotes, dashes, ellipses), since one curly apostrophe turns a 2x153-character message into 67-character UCS-2 segments.
- 2026-11-24 — (Part 04) `scripts/dev.py` injects dev-only defaults for unset channel secrets into its own child processes, so the demo works out of the box, while the app itself fails closed (503) without them.
