# Part 02 — Agent runtime + guardrails

## Goal
An agent that holds a multi-turn conversation, routes to the right AOP, follows it step by step, calls real (mock) tools, and **cannot** break policy no matter what the customer says, because guardrails run in code around the LLM.

## Scope
1. **Tools** (`src/baton/tools/`): implement every tool in the registry against mock commerce via httpx. Each tool: Pydantic input/output, description, `side_effect`, `requires_verification`, timeout + one retry on 5xx, maps API error codes to a `ToolError(code, customer_safe_message)`.
2. **Conversation state** (`src/baton/runtime/state.py`): conversation id, channel, customer_ref (None until identified), `verified: bool`, active `aop_id@version`, `current_step`, slots (order_number, etc.), turn count, escalation reason. Persisted in DB, loaded per turn.
3. **Agent loop** (`src/baton/runtime/agent.py`): `handle_turn(conversation_id, customer_message) -> AgentReply(text, status, trace_id)`.
   - Route (Part 01 router) if no active AOP or the customer changes topic.
   - Build system prompt: brand voice (`prompts/brand.md`), active AOP's policies, current step prompt, allowed tools for this step, state summary. Prompts are versioned files; the version goes in the trace.
   - Tool-calling loop with max 6 tool calls per turn; the LLM reports step progress via a `advance_step(target)` tool, which the runtime validates against the compiled graph (can't jump to a step with no transition).
4. **Guardrails** (`src/baton/runtime/guardrails.py`) — deterministic, run before every tool call and before every reply is sent:
   - **Identity gate:** any `requires_verification` tool is blocked until `verify_customer` succeeded in this conversation. Blocked calls return a tool result telling the LLM to verify first.
   - **Refund limit:** auto-approved refunds ≤ $100 (configurable) and ≤ remaining balance; above that → forced escalation.
   - **Tool allow-list per step:** only tools referenced by the current AOP step (plus read-only lookups) may run.
   - **Output checks** on the final reply: no promises of refunds/credits unless a refund tool succeeded this turn; no other customers' data (order numbers in reply must belong to this customer); PII redaction for anything echoed from tools besides the customer's own; length cap per channel.
   - **Loop/abuse detection:** escalate after 3 failed verification attempts, 12 turns without progress, or explicit "talk to a human".
   - Every guardrail decision (allow/block/rewrite/escalate + reason) goes in the trace.
5. **Escalation** (`src/baton/runtime/escalation.py`): sets status `escalated`, writes a handoff summary for the human (customer, intent, what was tried, what's needed) generated by the LLM, with a deterministic fallback.
6. **Traces**: one trace per turn with everything listed in CLAUDE.md. `GET /conversations/{id}/traces`.
7. **API**: `POST /conversations` (channel, optional customer hint), `POST /conversations/{id}/messages` → AgentReply, `GET /conversations/{id}`.
8. **CLI chat**: `uv run baton-chat` — interactive terminal chat against the local stack, `--trace` flag prints step/tool/guardrail info per turn. Needs a real key; with `BATON_LLM=fake` it prints a clear message.

## Acceptance criteria
- [ ] Tests (FakeLLM, mock commerce running in-process via ASGI transport) for full happy paths: where-is-my-order, cancel, return within window, subscription pause.
- [ ] **Adversarial guardrail tests** where the FakeLLM is scripted to misbehave and the runtime still holds: calling `create_refund` before verification → blocked; refund of $250 → escalated; reply saying "I've refunded you" with no refund tool call → rewritten/blocked; reply containing another customer's order number → blocked; tool not allowed at current step → blocked.
- [ ] `advance_step` to an invalid target is rejected and logged.
- [ ] Every turn has a trace including `aop_id@version`, prompt version, tool calls, guardrail decisions, token usage, latency.
- [ ] Logs contain no raw emails/phones (test with a log capture).
- [ ] `baton-chat --trace` works end to end with a real key (manual check; record a sample transcript in `docs/samples/chat-return.md`).
- [ ] Lint, types, tests clean.
